# 投稿規約・通報の運営手順

2026-10-02。実装はローカルに保持するが、今回の本番リリースには含めない（利用者による決定）。

## 今回のリリース判断

- 投稿規約への同意画面・同意記録、投稿通報、ユーザー通報、関連 Functions と投稿規約を要求する Firestore Rules は今回の本番反映対象から除外する。
- 理由：家族間のみの、既に信頼関係が構築されたコミュニティで使用するため、今回の製品には通報機能は不要との判断。
- 実装、関連テスト、運営手順、ブロック等の設計、ローカルプレビューは将来検討用に残す。この文書の後続部分は保留中の機能の仕様であり、今回公開する機能の説明ではない。
- 既存の安全案内、成人確認、保護者による利用許可・停止／再開と、そのサーバー側の制限は引き続き維持する。
- 現在の作業ツリーには保留機能のアプリ画面への組み込み・Functions の export・Rules の変更が含まれる。そのままリリースビルドや Firebase 一括デプロイを行わない。今回のリリース準備では、安全機能までを含む `08fa542` を基準とした独立したリリース用チェックアウトで、以後の必要な変更だけを選別し検証する。保留機能の有効化には改めて本番反映の判断が必要。
- この決定に伴う本番デプロイ・本番データ変更は実施していない。

## アプリとサーバー

- 投稿直前に投稿規約第1版を表示し、明示的な同意後に送信する。安全案内・成人確認とは別の同意。未同意でも許可済みチャットの閲覧・通報は可能。
- `acceptPostingTerms` が有効な家族メンバーを確認し、`chatAccess/{uid}` に版番号とサーバー時刻を記録。Firestore は未同意の直接投稿も拒否する。
- 投稿横のメニューから投稿・送信者を通報。チャット上部の旗から、投稿していないユーザーも通報できる。
- `reportChatAbuse` は認証、有効な所属、同じ家族内の対象、理由、補足1000文字以内を検証。子どもも保護者を通報できる。保護者の承認は不要。チャット利用許可とは別に所属を判定する。
- `moderationReports` はサーバー専用。家族管理者を含む全アプリ利用者の直接読み書きを拒否。投稿本文・送信者はサーバーで取得し証拠として保存。相手には通知しない。
- 通報はアカウント単位で30秒間隔。これは簡易連投防止であり、複数アカウント対策・自動検知・自動制裁ではない。
- 受付完了は画面に表示。自動メール、プッシュ通知、対応状況照会、運営専用画面は未実装。

## 公開前に運営が決めること

担当者と代行担当者、毎日の確認時間、緊急案件の連絡先、利用者への安全な連絡手段、証拠の保存期間を確定する。24時間監視や即時対応を約束しない。通報受付のみで運営が監視している状態とは扱わない。規約・プライバシー文書に通報時の情報利用と確定した保持方針を反映する。

## 受付から完了まで

1. 指定担当者が Firebase Console の `moderationReports` を確認。`status=new` を未処理キューとする。担当者用 IAM は個別アカウント・最小権限で運用し、共有ログインやアプリの familyAdmin 権限は使わない。
2. `status=triaged`、`assignedTo`、`reviewedAt` を記録。生命・身体の危険、子どもへの性的接触・搾取の疑いを最優先に確認。必要な緊急対応先への連絡は運営責任者が判断する。通報者の安全を損ねるおそれがあれば、対象の保護者に先に連絡しない。
3. familyId・対象 UID・投稿 ID と証拠を照合。必要な範囲だけ周辺情報を確認し、本文や通報者情報を外部チャット・通常ログへ転記しない。通報数だけで違反と決めない。
4. 違反なし／注意／投稿削除／利用制限を決定し、根拠と担当者を記録。誤認防止のため投稿削除・利用制限は別担当者が対象と影響を確認する。
5. 削除は対象 `families/{familyId}/messages/{messageId}` のみを信頼された管理権限で実施。利用制限は現状の所属 status だけでは保護者が戻せるため、恒久的な運営制裁として使わない。Firebase Auth の無効化・トークン失効も既存トークンへの即時停止を保証しない。サーバー専用の運営停止判定は下記設計を実装してから運用する。
6. `status=resolved` または `dismissed`、`resolution`、`resolvedAt`、`handledBy` を記録。訂正・異議申立ても元の reportId と結び付ける。連絡する場合は本人確認済みの安全な窓口を使い、通報者の身元や他人への処分詳細を相手に開示しない。
7. 保存期限を定期確認して証拠・補足を削除。保持例外は理由、承認者、再確認日を記録。アカウント削除時も reporterUserId・targetUserId・evidence と `moderationReportLimits/{uid}` を確認する。

## ブロック等の保護手段（設計・未実装）

第1段階は個人の「非表示・ミュート」。本人専用 `users/{uid}/chatBlocks/{targetUid}` に保存し、本人だけ読み書き可能にする。同一家族の相手か検証し、子どもが親も非表示にできる。本人の意思なく保護者が解除できない。相手に通知しない。過去・新規の本文、通知、検索結果を一貫して非表示とし、非表示投稿には自動既読を付けない。設定には一覧・解除と通報導線を置く。

共有チャットでの非表示は相手から自分の投稿が見えなくなる機能ではない。Firestore が本文を端末へ配信した後のフィルタリングである点も明示する。「相手との接触を完全に遮断」とは呼ばない。他メンバーによる引用や転送も防げない。

第2段階はサーバーでの接触遮断。個人ごとの配信先・サーバー仲介送信へデータモデルを変え、相互の本文・既読・通知・履歴の配信を止める。既存の共有 messages コレクションは全件取得するため、ブロック済み送信者だけ Rules で除外する設計にはしない。Rules はフィルターではなくクエリを拒否するため。グループへの影響・保護者の管理連絡をどう扱うかを別途決定する。

運営停止は `moderationRestrictions/{uid}` のサーバー専用記録を導入し、投稿・閲覧・招待・承認の全入口で確認する。保護者による status や利用許可変更では解除できないようにする。運営だけが理由・期限・解除履歴を管理し、通報や相談窓口は利用可能に保つ。稼働中の購読、キャッシュ、オフライン送信、複数端末、家族変更も検証対象とする。

公開判断では、非表示・ミュートの実装、運営担当の確保、通報の確認訓練、保持方針の確定を未完了として追跡する。

## 適用と検証

本番適用時は新しい Functions を先に用意し、規約同意・通報対応版アプリを配布したうえで投稿規約を要求する Rules に切り替える。旧アプリでは同意記録を作れず投稿が拒否されるため、更新案内と切替時点を決める。今回、本番デプロイは行っていない。

検証対象は `test/posting_safety_test.dart`（同意・拒否・通報・送信失敗）、`functions/moderation.test.cjs`（17件）、`firestore.moderation.test.cjs`（27件）、`firebase.flow.test.cjs`（登録・招待・承認・投稿・通報を含む22項目）。既存の安全確認・権限・招待テストと静的解析も実施。Functions の新規モジュール追加に伴い、承認テストのモックに読み込み先を追加した。
