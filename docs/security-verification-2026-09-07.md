# チャット分離・招待不正利用の検証

実施日：2026-09-07。対象：リポジトリの firestore.rules を読み込んだローカル Firestore Emulator。架空アカウント・家族のみ使用。本番にデプロイされているルール、実端末の招待URL起動、Cloud Functions の動作は今回の検証対象外。

## 結論

通常の他家族チャットへの直接アクセスは拒否される。ただし招待処理に迂回経路があり、「招待の不正利用も拒否される」とは判定できない。
既存 firestore.rules.test.cjs は成功。追加検証31項目は25項目成功・6項目失敗。失敗はテスト実行エラーではなく、拒否すべきリクエストが許可されたことを表す。

## 拒否を確認した操作

- 他家族および未認証ユーザーからのメッセージ単体閲覧、一覧取得、投稿、更新、削除。
- 自分の users ドキュメントの familyId・role を偽装した後の他家族チャット閲覧。
- 家族外からの招待作成、存在しない招待、使用済みの親招待。
- 使用済みのこども招待、トークン差し替え、別家族への参加先差し替え。
- 承認待ちのこどものチャット閲覧・投稿。
- こども招待を親メンバー登録に単純転用する操作。

正常系として同一家族の閲覧・投稿、有効な親招待による参加、有効なこども招待による承認待ち申請の成功も確認。

## 問題を再現した操作

| 操作 | 実際の結果 | 影響 |
| --- | --- | --- |
| 期限切れの親招待で参加 | 許可 | 期限切れ後も親メンバーになれる |
| 親招待のコード索引を消費せず、招待IDで参加 | 許可 | 対象の家族ID・有効な招待IDを知る認証済みユーザーが、コード確認を経ずに参加できる |
| 上記参加後に対象家族のチャット閲覧 | 許可 | 家族分離を招待処理経由で迂回できる |
| 期限切れのこども招待で申請 | 許可 | 期限切れでも承認待ち申請が作成される |
| こども招待を使用済みにせず申請だけ作成 | 許可 | トークンの一回限り利用をサーバー側で保証できない |
| 同じ未消費トークンで別ユーザーが再申請 | 許可 | 複数の承認待ち申請を作成できる |

こどもの申請成功は即時の家族参加ではない。今回、承認待ちユーザーのチャットアクセスは拒否された。

## 原因と修正方針

- firestore.rules:32 の isJoiningWithInvite は招待の期限、親招待の型、コード索引との対応・同時消費を確認していない。サーバー側で有効期限と索引の整合性を検証し、招待消費とメンバー追加を不可分にする必要がある。
- firestore.rules:144 の joinRequests 作成条件は、操作前の招待・トークンが active かを確認するが、有効期限と操作後の used への遷移を必須にしていない。getAfter による同時消費・usedBy の一致などを検証する必要がある。
- lib/repositories/invite_repository.dart:148 および :210 の期限確認はクライアント側。直接 Firestore へリクエストする検証では回避できた。

本検証では本体のルール・アプリ処理の修正や本番デプロイは行っていない。

## 再実行

app ディレクトリで実行：

```powershell
npm.cmd run test:rules
./node_modules/.bin/firebase.cmd emulators:exec --config firebase.audit.json --only firestore --project gyutto-rules-test 'node firestore.security-audit.cjs'
```

追加検証はテスト専用プロジェクト gyutto-rules-test のエミュレーター内データを初期化する。通常の8089番ポートとの競合を避け、監査用設定は8091番を使用。
